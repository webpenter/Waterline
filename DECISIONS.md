# WATERLINE — Decisions Log

An append-only log of technical and architectural decisions made during development.

| Date | Decision | Alternatives Considered | Reason | Reversibility |
| --- | --- | --- | --- | --- |
| 2026-09-21 | Established Phase 0 repository governance files (`CLAUDE.md`, `.cursor/rules/waterline.mdc`, `DECISIONS.md`, `DEVELOPMENT-PHASES.md`). | Implicit rules / ad-hoc decisions | Spec §1.1 mandates repository rules before feature code for AI build coherence. | High |
| 2026-09-21 | Single Next.js 15 repository with Payload 3 embedded. | Monorepo / split CMS backend | Payload 3 natively supports embedding into Next.js 15 App Router; avoids cross-origin and multi-server overhead. | Medium |
| 2026-09-21 | Pin to Next.js `15.4.11` and Payload `3.90.1` (`create-payload-app@3.90.1`). | Next.js 16 (latest, also in `@payloadcms/next` peer range) | Spec §1.1/§7 hard-requires "Next.js 15"; 15.4.11 is the newest 15.x release inside `@payloadcms/next@3.90.1`'s peer range (`>=15.4.11 <15.5.0`), confirmed via `npm view`. Revisit the Next 16 jump only after the spec is updated or at project close-out. | High — a version bump later is a routine dependency update, not a rewrite. |
| 2026-09-21 | Branch strategy: trunk-based off `main`. One `feat/NN-short-name` branch per §22/DEVELOPMENT-PHASES prompt (e.g. `feat/01-scaffold`). PR required, CI (typecheck/lint/test/build) must be green, squash-merge into `main`. Tag `main` after each merge as `vNN-name` (e.g. `v1-scaffold`) per spec §1.2. | Long-lived `develop` branch; direct commits to `main` | Matches the spec's own build loop (§1.2 step 6: "small, reversible commits... commit and tag"); keeps history linear and bisectable; one prompt = one reviewable unit. | High |
| 2026-09-21 | Environment-variable strategy: `.env.example` committed with every key from spec §7.3 (names only, no values). `.env.local` gitignored, one per developer/environment, never committed. A Zod-validated `/src/env.ts` parses `process.env` at process start and throws on missing/malformed vars before the app boots (spec Prompt 1 requirement). Runtime secrets for preview/production live in Vercel's environment-variable store (scoped per environment), not in files. CI secrets live in GitHub Actions repo/environment secrets. | `dotenv` with no validation; committing a real `.env` | Fail-fast beats a silent `undefined` reaching a DB client at runtime; keeps secrets out of git history entirely. | High |
| 2026-09-21 | Three environments: **development** (local `pnpm dev`, pointed at either local Docker services or cloud dev instances — see next decision), **staging** (a dedicated Vercel project/branch deployment, a separate Neon branch database, a separate Typesense collection prefix, `noindex` site-wide), **production** (Vercel production deployment, Neon main branch, Typesense production collection, real DNS). Staging and production are never allowed to share a database or search index. | Single shared "prod-like" environment; preview-deploys-only with no persistent staging | Prevents a bad migration or reindex in testing from touching real listings/leads; matches spec §7 stack (Vercel + Neon + Typesense Cloud) and §20 launch checklist's staging sign-off gate. | High |
| 2026-09-21 | Docker vs cloud dev services: **cloud services for this environment.** The sandbox this repo is developed in has no Docker installed and no passwordless `sudo`, so `docker-compose.yml` (Postgres+PostGIS, Typesense) is still authored per spec §7.2/Prompt 1 for contributors who do have Docker and for CI service containers, but day-to-day local development here runs against a free-tier Neon Postgres (with PostGIS enabled) branch and a free-tier Typesense Cloud cluster via `.env.local`. | Requesting Docker/sudo install; blocking all work until Docker is available | Neon and Typesense Cloud are already the spec's chosen production services (§7.1), so using them in dev too avoids maintaining two DB engines and matches "prod-like dev" instead of drifting from docker-compose. Needs the client/developer to supply a `DATABASE_URL` and Typesense credentials — flagged back to the user rather than fabricated. | High — `docker-compose.yml` remains available; switching back to local Docker later is a `.env.local` change only. |
| 2026-09-21 | Discovered mid-Prompt-1 that a second AI agent (Antigravity IDE) was concurrently scaffolding this same repository in parallel — it had already written `CLAUDE.md`/`DECISIONS.md`/`.cursor/rules/waterline.mdc` (near-identical to spec §1.1), a `package.json`, `env.ts`, `brand.ts`, `docker-compose.yml`, `.env.example`, and run `pnpm install`. Per user direction, reconciled the two in place rather than discarding either: kept Antigravity's `env.ts`/`brand.ts`/`docker-compose.yml`/`.env.example` (all already spec-accurate), added the entire missing Next.js App Router route tree (Payload admin UI + REST/GraphQL handlers + root layout — the app could not build or run without these), fixed a real bug where `next` had resolved to `15.5.25` (outside `@payloadcms/next@3.90.1`'s peer range, `>=15.4.11 <15.5.0`) by pinning exact versions, removed a duplicate/conflicting `vitest.config`, extracted the inline `Users` collection into `src/collections/`, added a `Media` collection, expanded `env.ts` to cover every `.env.example` var, made `/api/health` perform real DB/Typesense reachability checks instead of hardcoded strings, and replaced Antigravity's minimal CI workflow (typecheck/lint/test/build only) with one that also runs e2e, accessibility (axe), Lighthouse CI, and a bundle-size budget check against real Postgres+Typesense service containers, per spec Prompt 1's explicit CI list. Verified typecheck/lint/build/dev-server/health-route/lint-failure-gate all pass locally post-merge. | Discard one agent's work and rebuild from scratch; keep both scaffolds side by side unmerged | Antigravity's foundational config choices were sound and spec-compliant — rebuilding them would have been wasted, riskier duplication. The concurrent-write race caused one real build failure mid-merge (a file was read mid-write); the user paused the other agent before the merge was finished, after which the repo verified clean. | High — every file is inspectable; nothing was merged blindly. |
