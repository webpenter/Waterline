# WATERLINE — Decisions Log

An append-only log of technical and architectural decisions made during development.

| 2026-09-21 | Single Next.js 15 repository with Payload 3 embedded. | Monorepo / split CMS backend | Payload 3 natively supports embedding into Next.js 15 App Router; avoids cross-origin and multi-server overhead. | Medium |
| 2026-09-21 | Pin to Next.js `15.4.11` and Payload `3.90.1` (`create-payload-app@3.90.1`). | Next.js 16 (latest, also in `@payloadcms/next` peer range) | Spec §1.1/§7 hard-requires "Next.js 15"; 15.4.11 is the newest 15.x release inside `@payloadcms/next@3.90.1`'s peer range (`>=15.4.11 <15.5.0`), confirmed via `npm view`. Revisit the Next 16 jump only after the spec is updated or at project close-out. | High — a version bump later is a routine dependency update, not a rewrite. |
| 2026-09-21 | Branch strategy: trunk-based off `main`. One `feat/NN-short-name` branch per §22/DEVELOPMENT-PHASES prompt (e.g. `feat/01-scaffold`). PR required, CI (typecheck/lint/test/build) must be green, squash-merge into `main`. Tag `main` after each merge as `vNN-name` (e.g. `v1-scaffold`) per spec §1.2. | Long-lived `develop` branch; direct commits to `main` | Matches the spec's own build loop (§1.2 step 6: "small, reversible commits... commit and tag"); keeps history linear and bisectable; one prompt = one reviewable unit. | High |
| 2026-09-21 | Environment-variable strategy: `.env.example` committed with every key from spec §7.3 (names only, no values). `.env.local` gitignored, one per developer/environment, never committed. A Zod-validated `/src/env.ts` parses `process.env` at process start and throws on missing/malformed vars before the app boots (spec Prompt 1 requirement). Runtime secrets for preview/production live in Vercel's environment-variable store (scoped per environment), not in files. CI secrets live in GitHub Actions repo/environment secrets. | `dotenv` with no validation; committing a real `.env` | Fail-fast beats a silent `undefined` reaching a DB client at runtime; keeps secrets out of git history entirely. | High |
| 2026-09-21 | Three environments: **development** (local `pnpm dev`, pointed at either local Docker services or cloud dev instances — see next decision), **staging** (a dedicated Vercel project/branch deployment, a separate Neon branch database, a separate Typesense collection prefix, `noindex` site-wide), **production** (Vercel production deployment, Neon main branch, Typesense production collection, real DNS). Staging and production are never allowed to share a database or search index. | Single shared "prod-like" environment; preview-deploys-only with no persistent staging | Prevents a bad migration or reindex in testing from touching real listings/leads; matches spec §7 stack (Vercel + Neon + Typesense Cloud) and §20 launch checklist's staging sign-off gate. | High |
| 2026-09-21 | Docker vs cloud dev services: **cloud services for this environment.** The sandbox this repo is developed in has no Docker installed and no passwordless `sudo`, so `docker-compose.yml` (Postgres+PostGIS, Typesense) is still authored per spec §7.2/Prompt 1 for contributors who do have Docker and for CI service containers, but day-to-day local development here runs against a free-tier Neon Postgres (with PostGIS enabled) branch and a free-tier Typesense Cloud cluster via `.env.local`. | Requesting Docker/sudo install; blocking all work until Docker is available | Neon and Typesense Cloud are already the spec's chosen production services (§7.1), so using them in dev too avoids maintaining two DB engines and matches "prod-like dev" instead of drifting from docker-compose. Needs the client/developer to supply a `DATABASE_URL` and Typesense credentials — flagged back to the user rather than fabricated. | High — `docker-compose.yml` remains available; switching back to local Docker later is a `.env.local` change only. |
| 2026-09-21 | Discovered mid-Prompt-1 that a second AI agent (Antigravity IDE) was concurrently scaffolding this same repository in parallel — it had already written `CLAUDE.md`/`DECISIONS.md`/`.cursor/rules/waterline.mdc` (near-identical to spec §1.1), a `package.json`, `env.ts`, `brand.ts`, `docker-compose.yml`, `.env.example`, and run `pnpm install`. Per user direction, reconciled the two in place rather than discarding either: kept Antigravity's `env.ts`/`brand.ts`/`docker-compose.yml`/`.env.example` (all already spec-accurate), added the entire missing Next.js App Router route tree (Payload admin UI + REST/GraphQL handlers + root layout — the app could not build or run without these), fixed a real bug where `next` had resolved to `15.5.25` (outside `@payloadcms/next@3.90.1`'s peer range, `>=15.4.11 <15.5.0`) by pinning exact versions, removed a duplicate/conflicting `vitest.config`, extracted the inline `Users` collection into `src/collections/`, added a `Media` collection, expanded `env.ts` to cover every `.env.example` var, made `/api/health` perform real DB/Typesense reachability checks instead of hardcoded strings, and replaced Antigravity's minimal CI workflow (typecheck/lint/test/build only) with one that also runs e2e, accessibility (axe), Lighthouse CI, and a bundle-size budget check against real Postgres+Typesense service containers, per spec Prompt 1's explicit CI list. Verified typecheck/lint/build/dev-server/health-route/lint-failure-gate all pass locally post-merge. | Discard one agent's work and rebuild from scratch; keep both scaffolds side by side unmerged | Antigravity's foundational config choices were sound and spec-compliant — rebuilding them would have been wasted, riskier duplication. The concurrent-write race caused one real build failure mid-merge (a file was read mid-write); the user paused the other agent before the merge was finished, after which the repo verified clean. | High — every file is inspectable; nothing was merged blindly. |
| 2026-09-21 | Prompt 2 (design system) component scope: built the 11 base primitives DEVELOPMENT-PHASES.md's Prompt 2 entry names explicitly (Button, IconButton, Input, Select, Card, Badge, Modal, Tabs, Skeleton, LoadingState, ErrorState) plus an `AspectBox` wrapper for spec §9.3's fixed aspect ratios, rather than all 38 components spec §9.4 eventually lists. | Building the full §9.4 inventory now (PropertyCard, MapPanel, WaterCredentialsTable, NauticalPanel, FilterBar, ResultsList, LeadForm, LocaleSwitcher, etc.) | Most of §9.4's remaining components depend on domain types/data that don't exist until later prompts (Property collection is Prompt 3, search is Prompt 5/7, i18n is Prompt 6, leads are Prompt 12) — building them now would mean guessing at shapes and rebuilding later. Matches the spec's own incremental-prompt philosophy (§1.2, §2.5). | High — the remaining §9.4 components get added in the prompt that first needs them, on top of these same tokens. |
| 2026-09-21 | Tailwind v4 `@theme` CSS is generated from `src/tokens/tokens.ts` by `scripts/generate-tokens-css.mjs` (wired as `predev`/`prebuild`) into a gitignored `src/tokens/tokens.generated.css`, rather than hand-maintaining a parallel CSS token file. The generated `--font-display`/`--font-body` values prepend a `--font-display-loaded`/`--font-body-loaded` var (populated by `next/font/google` in `src/tokens/fonts.ts`) ahead of the literal spec §9.2 font stack, so the self-hosted font is actually used while `tokens.ts` itself stays byte-for-byte identical to the spec. | Hand-writing/duplicating token values in a `.css` file; changing the literal spec token strings to reference next/font's generated class names | `tokens.ts` is the single source of truth per §9.2's acceptance criterion ("changing color.abyss and font.display restyles..."); a generated artifact can't drift from it, and the font-loader var is purely a delivery mechanism, not a token value change. | High — regenerate via `pnpm tokens:build`. |
| 2026-09-21 | Prompt 3 scope decisions: (a) minimal **stub collections** for Agency, Agent, WaterBody, Destination so Property's relations exist — full versions land in Prompt 4 as the spec sequences them; (b) the admin **completeness meter** and custom warning UI deferred — Prompt 3's acceptance criteria test validation/fields/types, not admin chrome; the frontage warning ships as a field description, the meter arrives with the agency dashboard (Prompt 11/§8.10); (c) fingerprint uses coordinates+type+area-bucket+bedrooms now; the **perceptual image hashes** §8.8 also names are computed in the import pipeline (Prompt 11) where images are first processed; (d) DB-dependent acceptance criteria (publish rejection via API, EXPLAIN index usage, GIST verification) are encoded in `tests/int/property.int.spec.ts` and run in CI's Postgres+PostGIS service container, since this sandbox has no database; (e) `reference` uniqueness per agency enforced via a compound unique index `(agency, reference)`. | Building all of §9.4/§8 now; skipping integration tests entirely | Matches the spec's own prompt sequencing; keeps each commit reviewable. | High |
| 2026-09-21 | Self-hosted the display (Playfair Display) and body (Inter) fonts via `next/font/google` — variable-weight, `latin`+`cyrillic` subsets (2 files each = 4 files total, matching §13.3's "max four files"), `preload: true` only on the display font per §9.3 rule 7. Could not verify the actual font *fetch* in this sandbox — its egress proxy returns HTTP 404 for `fonts.googleapis.com`/`fonts.gstatic.com` (confirmed via `curl`; `registry.npmjs.org` and general internet both work), so `next build`/`next dev` fail here specifically on the font-fetch step. Verified everything else (typecheck, lint, full production build, dev server, all Playwright/axe tests, the dev-only 404 gate on `/dev/styleguide`) by temporarily stubbing `fonts.ts`'s exports, then restored the real `next/font/google` implementation before committing. | Switch to `next/font/local` with manually-sourced font files to route around the sandbox's network restriction | `next/font/google` is the standard, idiomatic self-hosting mechanism (Next.js downloads and serves the files from the same origin at build time — this *is* self-hosting, not a runtime Google Fonts dependency) and will work normally in any environment with ordinary internet access (a real dev machine, GitHub Actions, Vercel). Routing around a sandbox-specific proxy restriction with `next/font/local` would be solving a problem that doesn't exist outside this sandbox. | High — flagged here so the next session/developer knows to actually run `pnpm dev` once and confirm the fonts render, since this sandbox couldn't. |
| 2026-09-21 | Prompt 5 scope decisions: (a) getAggregatesForScope computes count/medians in the app over ≤1000 public rows — the §12 materialised views arrive with the performance pass (Prompt 17) once landing pages exist to feed; (b) getDestinationCounts uses per-destination `payload.count` (build-time call for landing tiles, not a hot path); (c) the Typesense search index only ever receives documents passed through the same §6.6 sanitizer as the public API (toSearchDocument → sanitizePropertyForPublic), so jittered/hidden coordinates hold across BOTH read paths; (d) filter values are backtick-stripped before entering Typesense filter_by strings so user input cannot escape its quoted token; (e) the automatic Postgres fallback is unit-tested with injected engines (healthy=false, and healthy=true+throw) — the live kill-Typesense test needs running services and belongs to CI/staging. | Materialised views now; SQL GROUP BY via drizzle; skipping fallback tests | Correct-first, optimize-when-measured (§12 sequences perf work explicitly); privacy rule §6.6 says "verify in the network tab" — same guarantee must cover the search index. | High |
