1. How the developer builds this (the operating method)
The target is 90–100 % complete before the client is involved. That requires discipline about how Cursor and Claude are used, not just
what is pasted into them.

1.1 Repository setup for AI-assisted development
Create these three ﬁles in the repo before writing any feature code. They are what keeps a long AI-assisted build coherent.
/CLAUDE.md — the project constitution, read by Claude Code and Cursor on every task:

# WATERLINE — project rules for AI assistants
## What this is
A worldwide property portal that lists ONLY properties with direct water access
(sea, ocean, lake, river, lagoon, canal, fjord). Next.js 15 App Router + Payload 3
+ Postgres/PostGIS + Typesense, deployed on Vercel.
## Non-negotiable rules
1. Performance budgets are acceptance criteria, not goals. Home first-load JS < 110KB
gzip, listing < 130KB, search < 160KB. LCP < 1.2s mobile. Never add a dependency
that pushes a route over budget — check with `pnpm analyze` before committing.
2. No component or route queries the database directly. Everything goes through
/src/lib/db with explicit return types.
3. No hardcoded colours, spacing, font sizes or radii outside /src/tokens. ESLint
enforces this; do not disable the rule.
4. Every public page is SSG or ISR. `force-dynamic` is forbidden on indexable routes.
5. Controlled enums over free text, always. If a field could be an enum, it is one.
6. The water rule: a listing cannot publish without >=1 waterAccessType and
distanceToWaterM <= 50. Never weaken this validation.
7. All user-facing strings come from /src/messages/*.json. No literal strings in JSX.
8. Sample/demo listings always carry isSample=true, render a SAMPLE badge, emit
noindex, and are excluded from sitemaps.
9. Accessibility: WCAG 2.2 AA. Every interactive element keyboard-reachable with a
visible focus ring. Never ship a div with onClick.
10. Multi-agency: every query that returns listings must respect agency scoping and
moderation status. An `agent` role never sees another agency's data.
## Definition of done for any task
- TypeScript compiles with zero errors (`pnpm typecheck`)
- ESLint passes (`pnpm lint`)
- Relevant tests pass (`pnpm test`), and new logic has a test
- `pnpm analyze` shows no route over its JS budget
- The feature works with JavaScript-heavy throttling (Slow 4G, 4x CPU)
- No console errors or hydration warnings

1.2 The build loop (repeat per prompt in §22)
1. Read the prompt and the spec sections it references.
2. Plan — ask Claude to produce an implementation plan and a ﬁle list before writing code. Reject the plan if it touches ﬁles outside
its scope.
3. Implement in a feature branch ( feat/07-search-page ).
4. Self-verify against the prompt's acceptance criteria — the prompt contains them explicitly; make Claude report pass/fail per line.
5. Measure — pnpm typecheck && pnpm lint && pnpm test && pnpm analyze . For UI work, run Lighthouse on the aﬀected route.
6. Commit and tag ( v0.7-search ). Small, reversible commits beat one giant diﬀ.
7. Log any decision in DECISIONS.md .

1.3 Context management
Keep open in Cursor: CLAUDE.md , the relevant spec section, /src/tokens/tokens.ts , /src/payload/collections/Property.ts , and the ﬁle
being edited. Do not paste the whole speciﬁcation into every prompt — it dilutes attention. Reference sections by number; the
prompts in §22 are self-contained.
When the context window degrades (repeated mistakes, forgotten conventions), start a new chat and re-anchor with: "Read
CLAUDE.md and /src/tokens/tokens.ts. We are implementing §X of the spec. Here is the current ﬁle."

1.4 Quality gates that run without the client
CI on every PR: typecheck, lint, unit tests, Playwright critical paths, Lighthouse CI budgets, bundle-size assertions, audit:seo
(canonicals, hreﬂang, JSON-LD validity, sitemap coverage), audit:a11y (axe-core on 8 key routes).
Weekly self-review: run pnpm audit:all and ﬁx everything before continuing to new features. Debt compounds faster in AIassisted builds than in hand-written ones.

2. Product definition
2.1 One-line deﬁnition
A global search engine for property you can step oﬀ and into the water — sea, lake, river, lagoon, canal or fjord — with the world's
only taxonomy built for people who own boats.

2.2 The hard rule (enforced in code)
A listing is admissible only with at least one qualifying waterAccessType and distanceToWaterM ≤ 50 . "Sea view", "500 m from the
beach", "walking distance to the lake" are rejections. Enforced by a Payload validation hook, surfaced to the submitting agency with a
clear reason, and logged.
This rule is the brand. If it leaks, we become a worse JamesEdition.

2.5 Two delivery tracks — do not mix them
Track A — public launch (Prompts 1–10, 12–20 of §22). Everything a visitor sees, plus the sample inventory, SEO, performance,
accessibility and deploy. This is the track that gets a complete, impressive, indexable site live fast, and it depends on nothing outside
the repository.
Track B — multi-agency supply (Prompt 11 of §22, plus §8). Roles, onboarding, bulk import, feeds, moderation queue, expiry
sweep, agency dashboard. Every ﬁeld it needs already exists in the data model from Prompt 3, so Track B can be built before or after
go-live without a migration or a rewrite.
Build Track A end to end ﬁrst. If the client wants inventory from external agencies on day one, run Track B before launch; if not, ship
Track A and add Track B in the following sprint. The spec is written so that either order works and neither delays the other.

3.0 Legal boundary
We replicate interaction patterns and information architecture — conventions, not property. We never copy HTML/CSS/JS,
scraped markup, photography, logos, licensed fonts, listing copy, editorial text, or a competitor's listing database. Scraping a
competitor's inventory is both a terms-of-service breach and a legal risk, and it is unnecessary (§13). "As good as JamesEdition" is the
target; "looks like JamesEdition" is not.

3.3 The competitive thesis
Incumbents are either broad and polished (JamesEdition, Christie's) or niche and dated (Vladi, Private Islands, Buy Waterfront
Worldwide). Nobody is niche, polished, fast and structured around water data. The moat is the data model (§6): expensive for others to
retroﬁt, free for us to own from day one.

4. Design and UX decisions (settled — do not re-open)
1. Editorial luxury, not portal chrome. Christie's restraint plus JamesEdition density. Large type, deep whitespace, no gradients, no
card drop-shadows, no pill-everything. Photography carries emotion; the UI gets out of the way.

2. Water is the visual system. Deep teal/ink palette with a warm sand accent (§9.2). A recurring 1 px horizon rule at section
breaks.
3. The map is a surface, not a tab. Persistent split view on desktop, toggle on mobile. Custom style: water saturated, land
desaturated.
4. Cards show water data. Price · location · frontage (m) · water body · access-type icon. Beds and baths are secondary. This
alone signals specialism in three seconds.
5. "Fits my boat" is the hero ﬁlter. A boat-length input sits on the homepage beside price and location. Most screenshot-able
feature on the site.
6. No hero carousel. One still image, or a muted ≤1.5 MB AV1 loop with a static poster. LCP depends on it.
7. No cookie wall before LCP. Consent is non-blocking, deferred, never layout-shifting.
8. Progressive disclosure on detail pages, with the water-credentials block as a designed table, not bullets.
9. Discretion controls exist on every listing (approximate coordinates, hidden address, unlisted visibility) — luxury sellers require
them, and they are three ﬁelds plus one map behaviour.
10. Empty states are computed, never generic: always name the most restrictive ﬁlter and oﬀer one click to relax it.

8.2 Agency onboarding
1. Agency applies at /list-with-us (company, country, website, licence number, contact, inventory size, how many listings have
direct water access).
2. Admin reviews, creates the Agency record and an agency_admin user; Payload sends a set-password email.
3. Agency completes its proﬁle (logo, description, languages, contacts) — proﬁle completeness is shown as a progress bar and gates
the ﬁrst publish.
4. Agency adds agents, then uploads listings by one of three routes (§8.3–8.5).
5. First ﬁve listings are reviewed manually; after a clean record, the agency can be promoted to tier = verified , which auto-approves
listings that pass automated validation.

8.3 Route A — manual entry
Payload admin with a custom listing form layout grouped as: Essentials → Water credentials → Nautical → Physical → Location →
Media → Content → Publishing. The water group sits second, not last, so it is never skipped. Live preview and a completeness meter
("Listings with frontage data receive 2.4× more enquiries — add it") are visible while editing.

Import ﬂow: upload → dry-run validation report (row-by-row: ok / warning / error with the exact reason and column) → the agency
ﬁxes and re-uploads or conﬁrms → import runs as a background job → summary email with a downloadable error CSV. Imports are
idempotent on (agency, reference) . Images are fetched, validated (≥1600 px, not a stock watermark, not a duplicate hash),
optimised and stored. An ImportJob record keeps the full audit.

8.5 Route C — XML/JSON feed
Documented inbound contract at /api/feeds/[agencySlug] with a per-agency token, supporting: our native JSON schema (published as
a JSON Schema ﬁle at /schemas/listing.schema.json ), plus adapters for the common shapes agencies already produce — Kyero XML,
Resales-Online, Houzez/WP REST export, and a generic mapped CSV over HTTP. Feeds are polled by a Vercel Cron job every 6 h; each
run produces a diﬀ report (created/updated/withdrawn/errors) emailed to the agency and visible in the admin. Listings absent from two
consecutive feed runs are moved to withdrawn , never deleted.
Field-mapping UI: for generic feeds, an admin screen maps source ﬁelds to our schema and stores the mapping on the Agency . Write
it once; it removes 80 % of onboarding friction.

8.6 Moderation workﬂow
draft → pending_review → approved (in_market) | changes_requested | rejected .

The review queue is a custom admin page showing side-by-side: submitted data, automated validation results, image quality ﬂags,
duplicate matches, and a map pin check. Automated pre-checks: water rule, coordinate plausibility (point must be within 200 m of a
water polygon — use a coarse coastline/water dataset, e.g. Natural Earth or OSM water polygons), price sanity versus destination
median, minimum 6 images, description length ≥ 300 characters, no phone numbers or emails in the public description, no ALL-CAPS
titles. Anything ﬂagged goes to a human; everything clean from a verified agency auto-approves.

8.7 Listing freshness
expiresAt = publishedAt + 180 days . At T-14 days the agency receives "conﬁrm these 12 listings are still available" with one-click
conﬁrmation per listing. On expiry the listing moves to expired : removed from search and sitemap, page returns 410 Gone with a
designed page oﬀering similar properties (§14.5). Stale inventory is the single biggest credibility killer in property portals.

8.8 Duplicate detection
Compute fingerprint from rounded coordinates (4 dp) + property type + built area bucket + bedroom count, plus perceptual hashes
of the ﬁrst three images. On a match: ﬂag in the review queue, let the admin link duplicateOf , and show only the canonical listing
publicly with "also listed by" agency attribution. Two agencies legitimately sharing a mandate is normal; two identical public pages is
an SEO and trust problem.

8.9 Lead routing and SLA
Lead → saved → routed to property.agent if set, else the agency's default lead inbox, else the internal desk. Email plus optional
WhatsApp deep link. Every lead has a status; if it stays new for 48 h the agency gets a reminder and the admin dashboard ﬂags it.
Response-time statistics per agency feed the tier decision. All lead emails are sent from our domain with reply-to the enquirer, so we
retain the record.

8.10 Agency-facing dashboard
A custom admin home for agency_admin : listings by status, listings needing attention (missing frontage, expiring, changes requested),
views and leads per listing over 30 days, average response time, feed health, and a "download your listing data" export. Give agencies
numbers and they keep the inventory fresh without being chased.

detail — so galleries feel authored rather than random.
13.2.3 Storage discipline. Always persist credit , licence , sourceUrl and sourceId on Media . Render attribution in the gallery footer
of sample listings. This makes the whole demo defensible in one line if anyone asks.
13.2.4 People imagery — a real rule, not a nicety. Never use a stock portrait of a real person as a ﬁctional agent. It
creates an identiﬁable person apparently endorsing a business they have never heard of, which is a personality-rights and GDPR
problem independent of the stock licence. For sample agents use: monogram avatars generated from initials in brand colours (a 20line SVG component), or silhouette placeholders. Real photographs only for real, consenting staﬀ.
13.2.5 AI-generated imagery. Acceptable for abstract editorial headers and texture, using a model whose terms permit commercial
use (Adobe Fireﬂy is the safest on training provenance; Flux and Midjourney are usable under their commercial tiers). Not acceptable
for listing photography, even in demo data: an invented photorealistic house presented as a property is exactly the
misrepresentation §13.12 exists to prevent. If used anywhere, record licence: 'ai-generated' and the model name on the Media
record.

13.7 Editorial copy — the writing brief and the AI workﬂow
The developer writes the editorial with AI assistance, following these rules. This is a legitimate, high-quality workﬂow; unreviewed AI
output is not.
Structure for every landing page (350–450 words): a 40–60-word direct answer paragraph opening the page · what the market is
like in one paragraph · what buyers actually get for the money, with real ﬁgures from our own aggregates · one paragraph of practical
speciﬁcs (mooring rules, access, seasonality, tenure quirks) · a closing line pointing to the listings. Two question-form H2s. No
adjectives that could apply to any coast.
Structure for a journal article (800–1,000 words): answer-ﬁrst opening, three to ﬁve H2s in question form, one table or list of
concrete ﬁgures, every non-obvious claim sourced with a link and a date, a short "what this means for buyers" close.
Four rules, non-negotiable:
1. Never publish a statistic the assistant produced from memory. Every number comes from a named source with a URL and a date, or
from our own database aggregates.
2. Every external claim carries an inline source and asOfDate .
3. The developer reads every published sentence. Anything that cannot be veriﬁed in 30 seconds is deleted rather than softened.
4. No AI-generated text about law, tax or residency status beyond describing that a rule exists and linking the oﬃcial source.
Article backlog for launch (pick 8): mooring and anchoring rules by country · buying a demanio marittimo concession in Italy,
explained · what "no ﬁxed bridges" means and why Florida buyers pay for it · dredging, draft and why depth at the dock matters ·
riparian rights versus foreshore ownership in England, France and Italy · ﬂood zones and coastal insurance · what a metre of private
frontage is actually worth · the ten best superyacht-capable private docks in the Mediterranean · lake versus sea: the trade-oﬀs
nobody explains · buying a private island: the eight questions to ask ﬁrst · canal houses in Amsterdam: what the deeds actually say ·
winterising a waterfront property.
Named sources to draw on (cite, never copy): Knight Frank and Savills research libraries, Eurostat and national statistics oﬃces,
Agenzia delle Entrate OMI quotations for Italy, HM Land Registry Price Paid data for the UK, Notaires de France, US county assessor
data and FRED, the BIS residential property price database, national maritime authorities for mooring rules. Quoting a sentence with

13.8 Listing descriptions — template grammar
Listing copy is generated, not written, from a slot grammar per locale in /src/content/description-templates/{locale}.ts :
{OpeningByType} {Positioning} {WaterSentence} {AccommodationSentence}
{OutdoorSentence} {NauticalSentence?} {LocationSentence} {ClosingByTier}

Each slot holds 6–10 variants selected deterministically by listing id, so no two listings read alike and re-running the generator is
stable. Example water sentences: "The property holds {frontage} metres of private {waterBody} frontage, with {beachType}
shoreline reached directly from the garden." Numbers always come from the structured ﬁelds, never from prose. This yields plausible,
locale-native copy at zero marginal cost and is also exactly how real agency descriptions get written.

16.1 Application security
Payload admin behind strong auth, 2FA required for admin and agency_admin ; server-side rate limiting on every public POST (leads

bundles; signed webhooks ( REVALIDATE_SECRET , CRON_SECRET , FEED_INGEST_SECRET ); dependency audit in CI; Sentry with PII scrubbing.

16.2 Multi-tenant security
A single tenant access function reused across collections; a Playwright test per collection asserting cross-agency access fails; AuditLog
on create/update/delete/publish/lead-view; uploaded media scoped to the owning agency; no agency can read another's leads, even
via the API.

16.3 Anti-scraping
Our listing data is the asset. Rate-limit and bot-challenge aggressive clients (Cloudﬂare rules), omit exact coordinates for
approximate_500m , never expose a public bulk JSON of all listings, watermark nothing but keep image URLs unguessable, and state the
prohibition in the Terms. Accept that determined scraping cannot be stopped — the goal is to make it costlier than it is worth without
harming legitimate crawlers.

16.4 GDPR
Non-blocking, deferred, granular cookie consent with a stored consent record; analytics only after consent where required; privacy,
cookie and terms pages live before launch; DPAs with Vercel, Neon, Cloudﬂare, Resend, Plausible, Typesense, Sentry; data-processing
register; a documented subject-access and erasure procedure with an admin action that anonymises a lead in one click.
